Project Management & Task Tracking System

Master Development Guidelines

Your requirements are organized into a proper Project Scope, Feature Roadmap, Architecture Standards, Security Standards, Agentic AI Skills, Testing Standards, and Development Workflow so that this document acts as the project's master development guideline.

The goal is not just to build a CRUD application. The goal is to build a polished, production-style, secure, modular, tested, documented and demonstrable full-stack engineering project.

2. Feature Roadmap With Dynamic Status

Status values:

- Done — implemented, tested and verified.
- In Progress — currently being implemented.
- Pending — not started.
- To Verify — implementation may exist but has not yet been properly verified.
- Blocked — cannot proceed because of a dependency/blocker.

Important Status Rule

Statuses must be updated whenever actual development progresses.

For example:

Pending
   ↓
In Progress
   ↓
Implemented
   ↓
Tested
   ↓
Verified
   ↓
Done

A feature must not be marked "Done" merely because code has been written.

Whenever a feature is successfully implemented and tested:

1. Update its status in the project roadmap.
2. Update "docs/PROGRESS.md".
3. Document important implementation details.
4. Add/update relevant tests.
5. Run the appropriate validation/security checks.
6. Commit the completed work.

If an existing feature is discovered to already be properly implemented and tested, update its status to Done after verification rather than rebuilding it.

13. Forgot Password and Email Reset

Implement a complete secure password-reset system.

Flow:

Forgot Password
      ↓
POST /api/auth/forgot-password
      ↓
Generate secure random token
      ↓
Hash token
      ↓
Store token hash + user + expiry
      ↓
Send reset email
      ↓
User clicks email link
      ↓
Reset Password page
      ↓
POST /api/auth/reset-password
      ↓
Validate token
      ↓
Check expiration
      ↓
Check single-use status
      ↓
Validate new password
      ↓
Hash new password
      ↓
Update password
      ↓
Invalidate reset token
      ↓
Invalidate existing sessions/refresh tokens where applicable

Reset tokens must:

- Be cryptographically random.
- Be short-lived.
- Be single-use.
- Expire after an appropriate period.
- Never be stored as plaintext.
- Be invalidated after successful use.

Recommended table:

password_reset_tokens
---------------------
id
user_id
token_hash
expires_at
used_at
created_at

Email service

Email functionality must be separated from authentication business logic.

AuthenticationService
        ↓
EmailService
        ↓
Email Provider

The provider should be replaceable without changing authentication business logic.

Potential providers:

- SMTP
- Resend
- SendGrid
- Other appropriate transactional email provider

Password-reset email should include:

- Application name.
- Password-reset explanation.
- Secure reset link.
- Expiration information.
- Security warning if the user did not request the reset.

15. Modular Architecture

Follow a modular monolith architecture.

Requirements:

- Separation of concerns.
- Reusable components/services.
- Business logic separated from API routes.
- Repository/service patterns where appropriate.
- Avoid unnecessary duplication.
- Consistent naming.
- Small focused modules.
- Avoid huge files/functions/classes.
- Avoid unnecessary abstractions.
- Avoid copy-paste architecture.
- Keep modules independently testable.

AI must not introduce abstractions simply because they appear architecturally sophisticated.

- [ ] SQL injection is prevented.

- [ ] Monitoring/health checks exist.

Code

27. Development Workflow

Branching

main
 └── Stable production

dev
 └── Active integration

feature/feature-name
 └── Individual development

Workflow:

1. Create feature branch from "dev".
2. Understand existing implementation.
3. Implement feature.
4. Add/update tests.
5. Run linting/type checks.
6. Run security checks where applicable.
7. Run agentic code-quality reviews.
8. Open PR into "dev".
9. Review and merge.
10. CI/CD runs.
11. Deploy to self-hosted environment.
12. Verify.
13. Update status to Done.
14. Update "PROGRESS.md".
15. Promote stable changes to "main" when appropriate.

28. Development Execution Rules

These rules govern how we work together:

1. Work incrementally, one day/task at a time.
2. First understand the existing codebase before modifying anything.
3. Never rebuild something already implemented and working.
4. Explain what we are building and why.
5. Give exact commands with the working directory.
6. Explain expected output of important commands.
7. Wait for confirmation before proceeding to the next day.
8. Maintain existing architecture and coding conventions.
9. Add/update tests for every module.
10. Perform appropriate security checks.
11. Use Archify when architecture/documentation needs updating.
12. Use Ponytail for engineering/code-quality review.
13. Use Unslop for AI-code quality/refactoring review.
